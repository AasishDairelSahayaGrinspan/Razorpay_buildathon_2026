The Problem

The Problem With AI Commerce

AI can make shopping genuinely conversational. But hand an AI agent direct control over carts, purchases, and payments and you create a trust and security problem: a model that can move money is a model that can be manipulated, hallucinate a price, or bypass an approval step.

Nimbus Commerce separates AI assistance from critical commerce and payment operations. The assistant lives in a read-only recommendation layer. Every money-moving step is an explicit user action, validated by the server, and recorded in an audit trail.

The Solution

A Safer Way to Shop With AI

Nimbus Commerce lets users interact with products conversationally while keeping money movement deterministic, secure, and explainable.

  • Real catalog recommendations — grounded in server data, never invented.
  • Server-authoritative prices — integer paise stored on the server.
  • Server-authoritative availability — active flag and inventory checked server-side.
  • User-controlled cart — the AI cannot add or remove items.
  • Explicit approval — a human approves every purchase intent.
  • Policy validation — 12 server-side checks run before payment intent.
  • Server-side Razorpay order creation — amounts never come from the browser.
  • HMAC payment verification — SHA-256 signatures verified server-side.
  • Verified webhooks — raw-body signatures checked before trust.
  • Payment state machine — explicit states, valid transitions only.
  • Complete audit trail — every meaningful action is recorded.
Features

Fourteen Decisions That Protect the Purchase

Every capability below exists in the repository. The pattern repeats throughout: the AI and the browser can read and recommend; the server owns price, approval, and payment state.

01

AI Shopping Assistant

Describe what you want in natural language and receive grounded recommendations from the merchant catalog, with explainable reasons and a confidence signal.

02

Real Product Catalog

Recommendations are based on actual catalog data — names, prices, inventory, and availability resolved server-side.

03

Server-Authoritative Pricing

Prices come from trusted server-side data in integer paise. Neither the AI nor the browser can redefine them.

04

Deterministic Cart

Cart totals and a canonical SHA-256 cart hash are calculated from trusted server data, not from client-supplied numbers.

05

Explicit Approval

The AI cannot approve purchases. The user must explicitly approve before checkout begins.

06

Razorpay Test Mode

Orders are created server-side using the Razorpay Orders API in TEST mode — no real money moves.

07

Payment Verification

Payments are verified using server-side HMAC SHA-256 signature verification.

08

Secure Webhooks

Razorpay webhook signatures are verified against the raw request body before the payload is trusted.

09

Payment State Machine

An eleven-state transaction machine with valid transitions only. DRAFT through APPROVED is pre-payment; order creation and payment outcome states are strictly enforced, with PAYMENT_SUCCESS, PAYMENT_FAILED, and PAYMENT_UNKNOWN as explicit terminal states.

See the diagram
10

Idempotency

Repeated checkout requests and duplicate webhook events are handled safely — no duplicate Razorpay orders, no duplicate transitions.

11

Retry Handling

Transient Razorpay failures (network errors and 5xx) are retried exactly once with bounded backoff. Validation errors are never retried.

12

Payment Failure Handling

Failed and unknown payment outcomes are represented as explicit, terminal states — never silently downgraded or auto-upgraded.

13

Audit Trail

Merchants can inspect the history of a transaction and understand exactly how it reached its final state.

14

AI Security Boundary

The AI agent is sandboxed to read-only catalog tools. An ESLint no-restricted-imports rule and a unit test enforce that it cannot import checkout, Razorpay, cart, approval, transaction, audit, webhook, or Prisma modules.

Razorpay Test Mode

How Razorpay Is Used

TEST mode

Nimbus Commerce processes no real money. Every order is created against Razorpay’s test environment, with server-side verification throughout.

  • Orders are created server-side.
  • Razorpay credentials remain server-side.
  • Payment verification happens server-side.
  • HMAC SHA-256 signature verification is used.
  • Webhook signatures are verified.
  • Browser input is never the payment authority.
  • The authoritative amount comes from the server-side transaction snapshot.

Webhooks

Verify First, Trust Second

HMAC SHA-256 shared webhook secret

Transaction Lookup by razorpay order id
State Handling payment.failed drives state

How it behaves

  • Raw request body is used for verification.
  • The signature is verified before the payload is trusted.
  • Invalid signatures are rejected and audited.
  • Unknown orders are acknowledged safely (no retry storm).
  • Duplicate webhooks are handled idempotently.
  • payment.failed can move valid pending/processing payments into PAYMENT_FAILED.
  • Successful transactions can never be incorrectly downgraded.
  • Webhook amounts are never treated as the authoritative transaction amount.

Retry behaviour — exactly as implemented

Order creation retries once on transient errors (network codes, timeouts, HTTP 5xx) with a 250 ms backoff. Validation, configuration, and 4xx errors are never retried, and PAYMENT_FAILED / PAYMENT_UNKNOWN are terminal — an operator creates a new transaction instead of auto-retrying a failed one.

Idempotency

Same Request, Same Result

Duplicate requests are normal: a retried request, a double-click, a re-delivered webhook. The system detects the duplicate and reuses existing state instead of double-charging.

Request 1 Create order
New Razorpay order created
Request 2 Detect existing order
Reuse existing state / order

Idempotency prevents duplicate Razorpay orders and duplicate state transitions. A unique constraint on cartId + cartHash guards approval, and a unique razorpayOrderId guards order creation. Duplicate webhooks on an already-successful transaction are acknowledged without re-processing, and a webhook can never downgrade a success.

Challenges

What Was Hard

Real obstacles, solved in the code — kept human and simple.

1

AI security boundaries

Keeping a helpful agent strictly read-only while it still feels useful.

2

Payment verification

Never trusting the frontend callback on its own — HMAC must win.

3

Webhook verification

Signing the exact raw body so whitespace tampering fails.

4

Server-authoritative pricing

Re-deriving every price and total on the server, ignoring the client.

5

Idempotency

Duplicate orders and webhooks must not double-charge or double-transition.

6

Payment failures

Representing failure explicitly instead of silently losing it.

7

UNKNOWN state

Deciding what happens when the upstream outcome is genuinely ambiguous.

8

E2E test stability

Making 282 Playwright tests deterministic under parallel workers.

9

Mobile layout issues

Chat, cart, and approval flows that hold up on small screens.

At one point everything broke at 2 AM. Red Bull was consumed. The agents were given more work. Somehow, it shipped.
